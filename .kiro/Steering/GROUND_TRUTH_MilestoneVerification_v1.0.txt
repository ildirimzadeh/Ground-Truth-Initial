# MILESTONE VERIFICATION PLAN
## GROUND TRUTH — For the Non-Technical Project Owner

---

## How to Use This Document

You are the project owner. Your job is to sit in front of the game, follow the numbered steps in each milestone, and compare what you **see on your screen** to what this document says you **should** see. You do not need to understand how anything works. You only need eyes, a mouse, a keyboard, and this document.

**Three possible outcomes for every test:**

- ✅ **PASS** — What you see matches exactly what this document describes.
- ⚠️ **PARTIAL** — Some parts match, some do not. Write down which step number failed and what you saw instead. Send it to the developer.
- ❌ **FAIL** — The result is completely wrong, or the game crashes, freezes, or shows an error window. Screenshot it. Send it to the developer.

**About the Debug Overlay:**
Starting in Milestone 1, the developer will build a small, semi-transparent panel in one corner of the game window. This panel shows you — in plain English — what the invisible systems are doing behind the scenes. You do not need to understand *why* these numbers exist. You only need to confirm they **change at the right time** and **show the right values** when this document tells you to look at them.

The overlay grows with every milestone. New fields are added on top of old ones. Old fields never disappear.

**TEST 2.1 — An Image Loads From JSON**

> **If this goes wrong:** If you see a blank white or grey rectangle instead of an image, the image file path in the JSON does not match an actual image in the project, or the image is not being loaded. If the overlay shows "LEVEL: null," the JSON did not load.

**TEST 2.2 — You Can Draw a Bounding Box**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Move your mouse cursor over the image. | The cursor is visible and responsive. No lag, no smoothing, no delay. |
| 2 | Click and hold the left mouse button at any point on the image. | A colored rectangle begins to appear at the point where you clicked. One corner is anchored where you clicked. |
| 3 | While holding the button, drag your mouse diagonally. | The rectangle stretches in real time, following your mouse exactly. It should feel instant — no rubbery or floaty movement. The box should be a bright, high-contrast color (neon magenta, green, or similar). |
| 4 | Release the mouse button. | The rectangle stays on screen. It does not disappear. The overlay updates: `BOXES DRAWN: 1`. |
| 5 | Draw a second box somewhere else on the image. | A second rectangle appears. The first rectangle is still visible. The overlay updates: `BOXES DRAWN: 2`. |

> **If this goes wrong:** If no rectangle appears when you click and drag, the drawing tool is not connected to mouse input. If the rectangle appears but is invisible (wrong color, zero opacity), it is a visual issue. If the box disappears when you release the mouse, the finalization step is broken. If the box appears but moves sluggishly or with visible delay, the input smoothing is not disabled.

---

**TEST 2.3 — You Can Tag a Box**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Draw a box on the image. | Box appears. `BOXES DRAWN: 1`. |
| 2 | Press the keyboard shortcut for "Combatant" (the developer will tell you the key — e.g., the `1` key) or click a "Combatant" button. | The overlay updates: `TAG SUBMITTED: Combatant`. The box on screen may change color or display a small label to show its assigned tag. |
| 3 | Draw a second box. Assign it the tag "Non-Combatant" (a different key or button). | The overlay updates: `TAG SUBMITTED: Non-Combatant`. `BOXES DRAWN: 2`. Both boxes are visible with their respective tags. |

> **If this goes wrong:** If pressing the tag key does nothing, the tag assignment is not connected to the box. If the tag applies to the wrong box (the first box instead of the second), the system is not tracking which box is "active."

---

**TEST 2.4 — The Timer Counts Down**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | When the image loads, look at the timer display on screen (a visible countdown number). | It shows a number (e.g., `5.0`) and immediately begins counting down. |
| 2 | Watch the overlay field `TIMER:`. | The number decreases every second: `5.0... 4.0... 3.0...` |
| 3 | Do nothing. Let the timer reach `0.0`. | The timer stops at zero. Something happens — either the image changes, a "Time's Up" message appears, or the system forces a failure. The overlay updates: `MATCH: NO`. |

> **If this goes wrong:** If the timer displays but never counts down, the countdown logic is not running. If the timer reaches zero and nothing happens (the screen just sits there), the timeout event is not firing.

---

**TEST 2.5 — Correct Box Gets a Match**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Load the test level. Read the `GROUND TRUTH:` coordinates in the debug overlay. These numbers tell you exactly where the "correct" box should be. | You see four numbers (e.g., `x:840, y:210, w:120, h:250`). |
| 2 | Draw a bounding box as closely as possible over the area described by those coordinates. Try to match it precisely. | Box drawn. `BOXES DRAWN: 1`. |
| 3 | Assign the correct tag. The overlay's `GROUND TRUTH` section or the level JSON tells you the required tag (e.g., "Combatant"). Press the corresponding key. | `TAG SUBMITTED: Combatant`. |
| 4 | Click the **Submit** button. | The overlay updates: `LAST IoU: 0.XX ✓` where `XX` is a number above `0.70`. `MATCH: YES`. |

> **If this goes wrong:** If `LAST IoU` shows `0.00` even though you drew the box in the right place, the coordinate system is misaligned — the game's pixel grid does not match where the overlay says the box should be. If `LAST IoU` shows a number above `0.70` but `MATCH` says `NO`, the tag comparison is failing even though the geometry is correct. If the submit button does nothing, it is not connected to the evaluation logic.

**TEST 2.6 — Wrong Box Gets a Miss**

**TEST 2.7 — Correct Box with Wrong Tag Gets a Miss**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Load the test level. Draw the box perfectly over the ground truth coordinates. | `BOXES DRAWN: 1`. |
| 2 | Tag it with the WRONG tag (e.g., if the required tag is "Combatant," tag it as "Non-Combatant"). | `TAG SUBMITTED: Non-Combatant`. |

> **If this goes wrong:** If the game says `MATCH: YES` even with the wrong tag, the tag comparison is not being checked — only the geometry. This is a critical failure.

**TEST 2.8 — Sabotage Detection**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Load the test level. Wait until the timer shows **more than 2.0 seconds remaining.** | Timer is above 2.0. |
| 2 | Quickly draw a box in a completely empty area (IoU will be 0). Tag it "Combatant." Submit immediately. | You submitted fast and confident, but at a completely wrong location. |
| 3 | Check the overlay. | `LAST IoU: 0.00`. `MATCH: SABOTAGE`. The overlay specifically identifies this as sabotage, not just a miss. |

Now test the opposite:

| Step | Action | What You Should See |
|:---|:---|:---|
| 4 | Load the level again. Wait until the timer is **below 2.0 seconds.** | Timer shows 1.9 or less. |
| 5 | Quickly draw a box in an empty area. Tag and submit. | `LAST IoU: 0.00`. `MATCH: NO` — regular miss, NOT sabotage. The game recognizes this as a panicked last-second mistake, not a deliberate act. |

> **If this goes wrong:** If both results show `MATCH: NO` with no sabotage distinction, the sabotage detection rule (IoU = 0 AND time > 2s) is not implemented. If both show `SABOTAGE`, the time check is being ignored.

---

**TEST 2.9 — Multiple Boxes: False Positives**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Load a level where the JSON defines exactly **one** target. | Overlay confirms: `GROUND TRUTH:` shows one set of coordinates. |
| 2 | Draw TWO boxes: one correctly over the target, one in an empty area. Tag both as "Combatant." Submit. | The overlay should show two results: Box 1 got a `✓` match, Box 2 got a `✗` miss (false positive). |

> **If this goes wrong:** If the game only evaluates the first box and ignores the second, multi-box evaluation is broken. If both boxes show `✓`, the system is not checking each box individually against the ground truth.

---

### Milestone 2 Completion Criteria

All nine tests pass. Drawing feels instant and responsive. IoU math produces correct and verifiable numbers. Tags are checked. Sabotage is distinguished from failure. Timeout is handled.

## MILESTONE 3 VERIFICATION: THE LOOP WITH CONSEQUENCES

**TEST 3.1 — Success Loads the Next Level**

## MILESTONE 4 VERIFICATION: THE SESSION STRUCTURE

### What You Are Testing
A full "shift" is now assembled from multiple levels, using the pacing curve. A receipt screen shows your performance at the end. The game tracks which day it is and can advance from Day 1 to Day 2. Rent is deducted at end-of-day.

### Debug Overlay — New Fields Added at Milestone 4

```
╔══════════════════════════════════════════════════╗
║  (all previous fields, plus:)                    ║
║                                                  ║
║  DAY: [number]                                   ║
║  PHASE: [OS_BOOT / INBOX / SHIFT_ACTIVE /        ║
║          RECEIPT / OS_DESKTOP / DAY_END]          ║
║  SHIFT QUEUE: [F, F, F, H, F, ...] ([current])  ║
║  SHIFT PROGRESS: [X] of [Y] levels              ║
║  ACCURACY: [XX%]                                 ║
║  MANIFEST: [day_XX_manifest.json]                ║
║  STORY EVENTS INCLUDED: [list of level_ids]      ║
║  PREREQUISITE CHECK: [event_id]: PASS/FAIL       ║
╚══════════════════════════════════════════════════╝
```

---

### Acceptance Tests

**TEST 4.1 — Shift Queue Is Assembled From JSON (Not Hardcoded)**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Start Day 1. Begin the shift. | The overlay shows `MANIFEST: day_01_manifest.json`. The `SHIFT QUEUE:` shows a sequence of letters like `F, F, F, H, F, F, H, F, ...`. The total count should be around 20 (or whatever the test manifest specifies). |
| 2 | Count the F's and H's. | The number of F's matches the `filler_count` in the manifest. The H's correspond to the story events listed in `STORY EVENTS INCLUDED:`. |
| 3 | Look at the pattern. | The letters follow the pacing curve (F's clustered at the start and middle, H's spaced according to the designed tension pattern). They are NOT in a random or purely alphabetical order. |

> **If this goes wrong:** If `SHIFT QUEUE` shows all F's with no H's, the story events are not being injected. If the queue is a random soup (like H, H, H, F, H), the pacing curve is not being applied. If the total count is wrong, the assembly logic has a counting error.

---

**TEST 4.2 — The Pacing Curve Places Levels Correctly**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Look at the `SHIFT QUEUE:` in the overlay. Note the position of the LAST entry. | The last entry should be `H` (a High-Stakes level). The GDD demands the shift ends on maximum tension. |
| 2 | Note the first 3 entries. | They should all be `F` (Filler). The shift must start easy. |
| 3 | Play through the first few levels. Notice that filler levels feel simpler (fewer targets, more time, less ambiguity) than high-stakes levels. | Filler levels are mechanically easier. High-stakes levels have tighter timers, more targets, or more complex scenes. |

> **If this goes wrong:** If the last level is an `F`, the pacing curve is misconfigured — the climax is missing. If the first level is an `H`, the ramp-up is broken.

---

**TEST 4.3 — Shift Progresses Through All Levels**

| Step | Action | What You Should See |
|:---|:---|:---|
| 1 | Start the shift. | `SHIFT PROGRESS: 1 of 20` (or whatever the total is). |
| 2 | Submit a box (correct or incorrect — either works). | The next level loads. `SHIFT PROGRESS: 2 of 20`. The `SHIFT QUEUE:` display highlights or marks the current position. |
