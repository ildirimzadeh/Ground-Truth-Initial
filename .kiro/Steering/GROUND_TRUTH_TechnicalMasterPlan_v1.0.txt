## PART II — DATA CONTRACTS

Every system below is defined by what data it accepts and what data it emits. These contracts are **binding** — any system built must conform to these interfaces exactly, or every downstream consumer will require refactoring.

---

### Contract 1: GlobalStateManager

| Direction | Data | Format |
|:---|:---|:---|
| **Receives** | A flag key and integer value | `SetFlag(string key, int value)` |
| **Receives** | A flag key and integer delta | `ModifyFlag(string key, int delta)` |
| **Emits** | An integer value for a given key (returns 0 if absent) | `GetFlag(string key) → int` |
| **Emits** | The entire flag dictionary (for serialization) | `GetAllFlags() → Dictionary<string, int>` |
| **Receives** | A complete flag dictionary (for deserialization) | `LoadAllFlags(Dictionary<string, int>)` |

**Canonical flag keys** (non-exhaustive; all authored in JSON, never hardcoded in game logic except these structural ones):

| Key | Type | Set By | Read By |
|:---|:---|:---|:---|
| `Corporate_Trust` | int | Submission Pipeline, Inbox choices, Level outcomes | Day 29 Bottleneck, Inbox prerequisites, Room Evolution |
| `Rebel_Sympathy` | int | Submission Pipeline, Inbox choices, Level outcomes | Day 29 Bottleneck, Inbox prerequisites, Room Evolution |
| `current_day` | int | Day Cycle Manager | Campaign Manifest, Inbox Manager, all prerequisite checks |
| `base_payout_modifier` | int (cents) | Wage Suppression | Level Manager (applied to LevelData.base_payout) |
| `timer_modifier_ms` | int (milliseconds) | Emotional Sink Modifiers, OS Store | Timer System |
| `iou_modifier_hundredths` | int (e.g., -10 = -0.10) | OS Store | Submission Pipeline (applied to minimum_iou) |
| `loan_balance_cents` | int | Debt Spiral | Economy Manager, Day Cycle Manager |
| `ending_condition` | int (0=unset, 1=A, 2=B, 3=C) | Day 29 Bottleneck | Ending System, Level Manager (Day 30) |

| Direction | Data | Format |
|:---|:---|:---|

## PART III — THE VERTICAL SLICE GATE

**Definition:** The Vertical Slice Gate is the precise moment at which the core loop is proven stable, data-driven, and scalable. **No narrative content, no commissioned art, no audio assets, and no world simulation features may be authored until this gate is passed.**

### What Must Exist and Work at the Vertical Slice Gate:

At the completion of this gate, a playtester — using only placeholder art (colored rectangles), placeholder text, and no audio — can perform the following sequence without encountering a hardcoded value, a broken transition, or a manual intervention:

1. **The game boots to the OS Desktop.** The desktop shell renders with a taskbar, wallet display, inbox icon, store icon, and hardware power button.

2. **The playtester opens the Inbox and reads an email.** The email was loaded entirely from a JSON file. It presents two choices. The playtester selects one. The choice writes a flag to the GlobalStateManager (verifiable in debug output).

3. **The playtester accepts a Gig Offer.** The screen transitions to the annotation software. The desktop UI is locked. A shift queue of exactly 5 levels has been assembled: 4 Filler, 1 High-Stakes, ordered by the pacing curve algorithm. All 5 levels were loaded from separate JSON files. No level data is hardcoded.

4. **For each level, the playtester:**
   - Sees a placeholder image displayed correctly.
   - Sees a countdown timer start at the JSON-specified duration (modified by any active GlobalStateManager flag, such as a cooling gel purchase).
   - Draws one or more bounding boxes using click-and-drag.
   - Assigns a tag via keyboard shortcut or dropdown.
   - Hits Submit.

5. **The IoU evaluation runs correctly.** A correct box + correct tag loads the `on_success` next level. An incorrect box or tag loads the `on_failure` next level. A timeout loads the failure branch. A deliberate zero-overlap sabotage box submitted with >2s remaining is flagged as sabotage and applies distinct flag changes.

6. **The Economy responds correctly.** The wallet display increases on success (with time-decay bonus visible), decreases on failure. Financial deltas match the JSON-specified values exactly.

7. **The shift ends.** A receipt screen displays: total levels, accuracy, total earned, total lost. The desktop unlocks.

8. **The playtester visits the Store.** They purchase one item (e.g., Cooling Gel). The wallet decreases. The item's effect is written to GlobalStateManager.

9. **The playtester clicks the power button.** Daily rent is deducted. The Day counter increments. The game auto-saves. The game reboots to Day 2.

10. **On Day 2, the consequence is visible.** The email choice from Day 1 has caused a different email to appear in the inbox (via `delay_days` and `next_thread_id`). AND/OR: the flag set on Day 1 has caused a different story level to appear in today's shift (via the prerequisite system in the Campaign Manifest). The Cooling Gel purchase has measurably increased the timer duration for all levels.

### What This Proves:

- The JSON Data Pipeline correctly deserializes all three data types (levels, emails, manifests).
- The GlobalStateManager is the single source of truth, and every system reads/writes through it.
- The Event Bus correctly decouples the Submission Pipeline from the Economy, the Timer from the UI, and the Day Cycle from the Inbox.
- The Level Manager assembles queues dynamically from filtered pools — not from hardcoded sequences.
- The prerequisite system works: a Day 1 flag change produces a Day 2 content change.
- The economy creates real pressure: income is insufficient to trivially cover expenses.
- The Save System persists all state across a simulated session boundary.
- **Every system above the Vertical Slice Gate line can accept unlimited new JSON content files without any code changes.**

## PART V — THREE HIGHEST-RISK ARCHITECTURAL DECISIONS

---

### RISK 1: The GlobalStateManager as Single Source of Truth

**The Trap:** Creating multiple state-tracking systems — an economy manager with its own internal flags, an inbox manager that tracks narrative state separately, NPC scripts that remember their own history. Over 30 days of campaign, these parallel state stores inevitably desynchronize. Save/load becomes a nightmare of serializing six different objects. Adding a new cross-system consequence (e.g., "sister's death affects the timer") requires touching three systems that don't know about each other. By Day 15, the developer is debugging phantom flag mismatches instead of authoring content.

**The Correct Approach:** One dictionary. One access pattern. Every system in the game reads and writes through `GlobalStateManager.GetFlag()` and `SetFlag()`. The Economy Manager does not store "has_cooling_gel" internally — it reads it from the flag dictionary. The Timer System does not store its modifier — it reads `timer_modifier_ms` from the dictionary on each level load. The Inbox Manager does not evaluate narrative state from its own records — it queries the dictionary. This means the Save System serializes exactly one `Dictionary<string, int>` plus the Economy balance and the Inbox pending queue. Cross-system consequences are trivial: any system can set a flag, and any other system can react to it, with zero coupling between them. The dictionary is the game's single canonical state. If it is accurate, the entire game is accurate.

---

### RISK 2: Coupling the OS Desktop to the Drone World

**The Trap:** When building the "Flashbang" button or the "Offer Bribe" chat option, the natural instinct is to give the UI button a direct reference to the `PoliceOfficer` or `Terrorist` GameObject in the scene. This works for the first prototype. Then the developer adds a second tactical action, and now the chat UI has references to two NPC types. Then a third. Then the NPCs need to react to *combinations* of actions. By Milestone 7, the `ChatWindow.cs` script imports every NPC type in the game, and adding a new tactical option requires modifying both the UI code and every NPC script. A single refactor cascades across the entire project. Additionally, UI elements and world-space NPCs exist in different scenes or canvases — direct references break when levels reload.

**The Correct Approach:** The ScriptableObject Event Bus as defined in Contract 2. The UI button knows only the event channel asset — it calls `OnTacticalAction.Raise(TacticalAction.Flashbang)`. The NPC state machine knows only the same event channel asset — it subscribes in `OnEnable`, unsubscribes in `OnDisable`. Neither system imports, references, or is aware of the other. Adding a new tactical action requires: (1) creating a new enum value, (2) adding a button that raises it, (3) adding a handler in the NPC state machine. Zero existing code is modified. The Event Bus pattern must be established in Milestone 1 and used universally — if even one system bypasses it with a direct reference, the architecture's decoupling guarantee is void.

---

### RISK 3: Hardcoding the 30-Day Campaign Sequence

**The Trap:** Building Day 1 as a scene. Building Day 2 as a scene. Writing `if (currentDay == 5 && rebel_trust > 2)` in the Level Manager. Authoring a `switch` statement with 30 cases. This feels productive in Week 1 because each day is "done." By Day 10, the developer realizes that adding a new side quest on Day 7 requires modifying the Day 7 case, the Day 12 case (where the consequence lands), the Day 20 case (where the second consequence lands), and the Day 29 bottleneck evaluation. A single new narrative thread touches 4+ code locations. By Day 20, the branching logic is an unmaintainable web of cross-referencing conditionals. The GDD explicitly warns against this as "spaghetti code."

**The Correct Approach:** The "Flag and Prerequisite" system described in the GDD. Each day is a DayManifest JSON (not a scene, not a code case). Each story event is a self-contained JSON with its own `prerequisites` dictionary. The Level Manager's day-assembly logic is a single generic loop: iterate the event pool, check each event's prerequisites against GlobalStateManager, include qualifying events, fill remaining slots with filler. This loop is written once in Milestone 4 and never modified again. Adding a new side quest means writing one new Level JSON with the correct prerequisites and adding its `level_id` to the appropriate DayManifest's `story_event_ids` array. Zero code changes. The developer's content authoring workflow, for the entire second half of production, is writing JSON files and creating art assets — not touching the codebase. If the prerequisite system is compromised or bypassed even once with a hardcoded check, it creates a precedent that erodes the entire data-driven architecture.
